# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Work is tracked in GitHub Issues. The milestone 1 spec is #1 and its tickets are its sub-issues; #2 and #3 outline the later milestones. Read the spec before proposing structure or tooling.

## Commands

All Compose commands run from the repo root. Copy `.env.example` to `.env` first.

- Run the stack: `docker compose up -d --build --wait`, then <http://localhost:8080> (`CADDY_PORT`). Stop with `docker compose down` (`-v` deletes data).
- Dev mode (hot reload for API and frontend): `docker compose -f compose.yaml -f compose.dev.yaml up -d --build --wait`. Dev images are separate from prod ones; `--build` picks up dependency changes.
- Backend tests (real Postgres, Redis, MinIO, so run inside Compose): `docker compose -f compose.yaml -f compose.dev.yaml run --build --rm api pytest`
- One backend test: `... run --build --rm api pytest tests/test_health.py::test_live_reports_ok`
- Clear the response cache by hand (seed does it on its own): `docker compose run --rm api python -m app.clear_cache`.
- Seed content by hand (the stack runs it at startup, non-strict): `docker compose run --rm seed python -m app.seed`. Add `--strict` to fail while any `PLACEHOLDER:` remains or a media file is missing. In dev mode, add `-f compose.yaml -f compose.dev.yaml` before `run`.
- Pre-render again after a manual seed (writes the pages Caddy serves from the current content, no rebuild, about a second): `docker compose run --rm --no-deps prerender`. `--no-deps` stops Compose starting the seed again first. The stack runs it at every start, after the seed.
- Frontend tests: `cd frontend && npm test`. One test: `npx vitest run src/pages/ReadinessPage.test.tsx -t "unreachable"`. `npm test` includes the token and contrast checks
- Observability profile (optional; Prometheus, Loki, Tempo, Alloy, Grafana): set `GRAFANA_ADMIN_PASSWORD`, `GRAFANA_DB_PASSWORD` and `OTEL_EXPORTER_OTLP_ENDPOINT=http://collector:4318` in `.env` (see `.env.example`), then `docker compose --profile observability up -d --build --wait`; Grafana is at <http://localhost:3000> (`GRAFANA_PORT`, bound to 127.0.0.1). Without the profile nothing extra runs. Static checks that need no stack: `cd backend && uv run python ../infra/observability/check_config.py`. In dev mode put `-f compose.yaml -f compose.dev.yaml` before `--profile`.
- Backend lint and types (host, in `backend/`): `uv run ruff check . && uv run ruff format --check . && uv run pyright`
- Frontend lint and types (in `frontend/`): `npm run lint && npm run typecheck`
- The frontend uses npm.
- Browser tests (Playwright, `frontend/e2e/*.spec.ts`, config in `frontend/playwright.config.ts`; ticket #19 adds the Climb's own): start the stack, then `cd frontend && BASE_URL=http://localhost:8080 npm run e2e` (use your `CADDY_PORT`). Chromium runs with software WebGL; locally it uses `/usr/bin/google-chrome` (or `CHROME_PATH`), otherwise run `npx playwright install chromium`. Tests force tiers with `?tier=` and never depend on real frame timing; the browser's user agent is set to an ordinary one because the API drops `HeadlessChrome` as a bot.
- Re-capture the still images (after any change to the scene, the Hiker's model, a `--color-*` token or the script): stack up, then `cd frontend && npm run stills -- --base http://localhost:8080`, look at the 14 files in `content/stills/` and commit them, then `docker compose run --rm seed python -m app.seed` to publish them. `npm test` fails (`src/still/stillsFresh.test.ts`) when `content/stills/stills.json`'s fingerprint no longer matches the scene's inputs (`frontend/scripts/stills-fingerprint.mjs` lists them), and so does CI.
- CI (`.github/workflows/ci.yml`) runs on pull requests and pushes to `main` as five parallel jobs: backend lint and types, the observability config checks, backend tests (the same Compose command as above, with `.env` copied from `.env.example`), frontend lint, types, tests and build (the build includes the pre-render's server bundle), and the browser tests (builds the production stack, which runs the `prerender` job so a pre-render that cannot draw a page fails the stack, checks the sitemap and a 404, installs Chromium, runs `npm run e2e`).

## Architecture

Caddy is the only published port. It serves the built frontend's assets (baked into its image), the pre-rendered pages (from the `site` volume, mounted read-only at `/srv/pages`) and proxies `/api/` to FastAPI. In dev mode it proxies `/` to the Vite dev server instead. Postgres, Redis and MinIO are internal. Four one-shot services run at startup: `migrate` (Alembic), `seed` (after `migrate`; the API waits for it), `minio-init` (creates the bucket) and `prerender` (after the API is healthy, so after the seed; Caddy waits for it).

- `backend/app/`: `api/v1/` routes call `services/`, which use probes and clients from `data/`. `deps.py` wires them with FastAPI dependency injection; `main.create_app` builds the clients at startup. Settings come from environment variables only (`config.py`).
- Content: `content/*.yaml` (profile, Stages, Projects) is mounted read-only at `CONTENT_DIR` (`/content`). `app/content/` validates it (`schema.py`, `loader.py`); `app/seed.py` loads it through `ContentRepository.sync`, which upserts on Stage key / Project slug and deletes rows missing from the files. Position is the file order. The profile is one JSONB row; Stages and Projects are tables. Alembic revision `0002` holds the schema.
- Media (`app/media/`, `content/media.yaml`): the seed's second step prepares the Portrait, Video CV and CV PDF from `MEDIA_DIR` (default `./my_docs`, mounted read-only at `MEDIA_SOURCE_DIR` `/media-source`; `my_docs/.gitkeep` is tracked so a clone has the folder and Docker never creates it as root). `manifest.py` validates the manifest (bare file names only), `images.py` makes widths in AVIF, WebP and JPEG (orientation applied, sRGB converted, all metadata dropped), `video.py` runs ffmpeg (HDR HLG/PQ goes through a zscale/tonemap chain to SDR BT.709; 1080p and 720p, `+faststart`), `prepare.py` names every object by content hash, `pipeline.py` syncs one role at a time: skip when the source is absent (strict fails, naming the files), leave alone when the source SHA-256 and the settings hash (widths, qualities, ffmpeg arguments) match the `media_items` row and the objects exist, otherwise upload, record, delete the old keys. A final sweep deletes bucket objects no row refers to. `data/storage.py` `MediaStore` applies the public-read bucket policy (GetObject only, so no listing or writes) at every seed. `media_items` (Alembic `0004`) has one row per role with a JSONB list of variants; `GET /api/v1/media` maps keys to `/media/<key>` addresses. `infra/caddy/media.caddy` (imported by both Caddyfiles) serves `/media/*` from MinIO: reads only, flat object names only (`[A-Za-z0-9_-][A-Za-z0-9._-]*`) and no query strings, immutable cache header on 200/206/304, every error answered as a plain 404 with no upstream body, MinIO headers stripped. Directive order matters there, so the steps sit inside a `route` block. ffmpeg is installed in the `dev` and `seed` image targets only, never `prod` (the API). Media tests use generated fixtures (`tests/media_helpers.py`), a throwaway bucket and the `_test` database, and never the real files.
- The Summary waits for `/media` to settle (failure counts as no media) so the Portrait is in the first paint with explicit dimensions. `components/Portrait.tsx`, `VideoCv.tsx` (`preload="none"`, 720p and a smaller poster below 768px) and `CvDownload.tsx` draw nothing when their role is absent. On `lg` screens the identity column (Portrait at 160px, name, headline, contacts, CV download) must fit the first screen at 1280x800; it sticks only on viewports at least 50rem tall (the `tall` variant, a `@custom-variant` in `index.css`, the one literal allowed outside `@theme` because media queries cannot read tokens) and scrolls with the page on shorter ones.
- A Challenge written as `PLACEHOLDER: text` is stored without the marker plus `challenge_is_placeholder`. Strict seed lists every `PLACEHOLDER:` in any text field and loads nothing. Stage keys are fixed by `StageKey` in `schema.py`; Visits depend on them.
- Content tests run against a throwaway `<POSTGRES_DB>_test` database (created and migrated per session in `tests/conftest.py`), never the stack's own data. The suite also checks that `content/` validates and has no phone-shaped text.
- Logs are JSON through structlog, including uvicorn's. `middleware.py` binds `X-Request-ID` (accepted or generated) to every line and logs one `request` line per request. Uvicorn's access log is off because it prints client IPs, which ADR 0002 forbids.
- **Response cache (ticket #12). Rules that must not be broken**: only the five read endpoints are cached (`/profile`, `/stages`, `/projects`, `/projects/{slug}`, `/media`). Never cache anything per Visitor, a Visit or contact response, the health endpoints, an error, or a "not seeded" 503; `NoStoreMiddleware` marks every other `/api/` answer `Cache-Control: no-store` by default, so a new endpoint is uncached until it opts in. Cache keys never contain a Visitor, an address or any request value except a slug that already exists in the Projects list.
- Response cache, how it works: `data/response_cache.py` (`ResponseCache`) is the only place that talks to Redis for it; `ContentService` and `MediaService` call `get_or_load(endpoint, name, load)` and return JSON bytes, and `api/v1/http_cache.py` turns those into a 200 or 304 (strong `ETag` = SHA-256 of the body, `Cache-Control: no-cache`, weak comparison, list form and `*` handled). Keys are `api-cache:<generation>:<name>`; the generation token lives at `api-cache:generation`. **Invalidation is by the seed**: after each seed step commits (content, then media, the latter in a `finally`), `app.seed.invalidate_cache` stores a new random generation and purges the old entries. Readers read the generation before they load from Postgres and store under that generation, so a request that was mid-load when the seed finished can only write into an abandoned namespace and never serves stale content; do not invalidate before the commit, and do not read the generation after the load. A seed that cannot reach Redis exits 1 saying so (re-run it). The 1 hour expiry (`CACHE_TTL_SECONDS`) is only a safety net and cleans abandoned generations. Everything is under the `api-cache:` prefix; clearing (`docker compose run --rm api python -m app.clear_cache`) never flushes a database or touches `visitor-salt:` or `rate-limit:`. Unknown slugs are answered from the cached Projects list (no query, no key); malformed slugs are refused before Redis is asked.
- Redis is optional for the cache: reads and writes have a 0.25 s timeout (`CACHE_TIMEOUT_SECONDS`, its own client with no retries), and after a failure the cache is skipped for 5 s (`CACHE_RETRY_SECONDS`), so a dead Redis costs one timeout, not one per request, and logs one `cache_unavailable` warning (error class only) per minute at most, then `cache_recovered`. Tests use Redis database 15, emptied before each test (`conftest.py`), never the stack's database 0.
- Metrics (`app/metrics.py`): `portfolio_cache_hits_total{endpoint}`, `portfolio_cache_misses_total{endpoint}`, `portfolio_cache_errors_total{endpoint,operation}` (operation `read`, `write` or `skipped` while the cache is being skipped). Endpoint is one of `profile`, `stages`, `projects`, `project`, `media`; a `project` miss also looks up the Projects list, which counts under `projects`. They are served by a second small ASGI app at `/metrics` on `METRICS_PORT` (9100, 0 disables), inside the API process, unpublished and outside `/api/`, so Caddy (which proxies only `/api/*`) cannot reach it. Ticket #13 adds request metrics to `app.state.metrics_registry` and points Prometheus at `api:9100/metrics`. Labels never carry anything about a Visitor.
- **Telemetry (ticket #13). Rules that must not be broken**: no span, metric label or log line may carry a client address, `X-Forwarded-For`, a user agent, a referrer, a Visitor hash, the daily salt, a rate-limit key, or a contact message's name, address or text. This is kept true by never capturing, not by filtering: the stock OpenTelemetry instrumentations are **not installed** (they record `net.peer.ip`, `http.user_agent`, forwarded-for and statement text). `app/telemetry.py` makes the spans by hand with a fixed attribute list: request span (`http.request.method`, `http.route`, `http.response.status_code`), database span (`db.system`, `db.operation` = the statement verb only, via SQLAlchemy cursor events that never read the statement or parameters) and Redis span (`db.system`, `db.operation` = the command name, never a key or value; `TracedRedis` and `TracedPipeline`). Exceptions are never recorded on a span (their text can carry statement parameters), only `error.type` = the class name. Incoming `traceparent` is not read. Do not add `opentelemetry-instrumentation-*` packages or span attributes taken from the request, and keep `tests/test_telemetry.py` passing: it exports spans from a scripted Visit and contact message and searches them and the metrics for the address, user agent, referrer host, hashes, salt, rate-limit keys and the message.
- Telemetry, how it works: `TelemetryMiddleware` is the outermost middleware, so its span is current while `RequestIdMiddleware` writes the `request` line and the structlog processor `add_trace_ids` adds `trace_id` and `span_id` to every line written inside a request (also uvicorn's and SQLAlchemy's, through the foreign chain). The route comes from the router after matching (`route_template`: the router keeps routes relative, so the `/api/v1` prefix is recovered from the path text before the matched part); no match is `unmatched`, so a Visit ID or a slug is never a span name or label, and an unknown HTTP method becomes `OTHER`. `/api/v1/health/live` (the container healthcheck) is counted but not traced. Database and Redis work outside a request is not traced. Spans are exported over OTLP/HTTP only when `OTEL_EXPORTER_OTLP_ENDPOINT` is set (`create_tracer_provider`); unset, spans are made (so logs still have a trace ID) and dropped, and nothing connects anywhere. `create_app(tracer_provider=...)` lets tests collect spans in memory.
- Request metrics (`app/metrics.py`, same registry as the cache's): `portfolio_http_requests_total{method,route,status}`, `portfolio_http_request_duration_seconds{method,route,status}` (histogram), `portfolio_db_pool_connections{state="in_use"|"idle"}` and `portfolio_db_pool_max_connections` (a collector reading the pool when scraped; the pool is 5 plus 10 overflow, set in `data/db.py`).
- Observability profile (`infra/observability/`, services in `compose.yaml` under `profiles: [observability]`): Prometheus scrapes `api:9100`; Alloy (`collector`) tails this Compose project's container logs through `docker-proxy` (tecnativa/docker-socket-proxy: the Docker socket is mounted only there, read-only, and only GET for containers and networks pass) into Loki with one label, `service`, and receives the API's OTLP traces on 4318 for Tempo. Retention: metrics 7 days (1 GB cap), logs 7 days, traces 3 days. Every container has `mem_limit`. Only Grafana publishes a port (127.0.0.1). Grafana is provisioned from `grafana/provisioning` and `grafana/dashboards` (`allowUiUpdates: false`; edit the JSON). Data sources have fixed uids (`prometheus`, `loki`, `tempo`, `postgres`) which dashboards refer to; `check_config.py` fails CI when one does not match. The `grafana-setup` job is what Grafana waits for: it exits 1 naming the missing variable unless both passwords are set (a `:?` in `compose.yaml` would also fire with the profile off), then creates or updates the `grafana_reader` role with `setup-grafana.sh` (password via `\getenv`, never on a command line, statement logging off for the session; SELECT on every table and view in `public`, read-only sessions; it re-runs on each `up`, so a later migration's tables are granted on the next one). Grafana's admin password applies only when its database is first created; change it later with `docker compose exec grafana grafana cli admin reset-admin-password ...`. Every query on the Visits and Progress dashboard uses `$__timeFilter`, so the dashboard queries `visit_progress` with a time filter instead of reading the unfiltered `visits_per_stage` view.
- Caddy caching: `/assets/*` (Vite's hashed scripts, styles and fonts) gets `public, max-age=31536000, immutable` only when the file exists; everything else static, the HTML document and the favicon included, gets `no-cache` and revalidates through file_server's ETag. `infra/caddy/compress.caddy` (a snippet imported by both Caddyfiles) compresses text and JSON with zstd or gzip and is not used for `/media/`. Caddy's `encode` appends `-gzip` or `-zstd` to the ETag of what it compresses, so the API route restores `If-None-Match` with `header_up`; without it a compressing browser never gets a 304 from the API.
- Readiness (`/api/v1/health/ready`) pings each dependency with a short timeout and returns 503 with per-dependency status when any fails.
- Frontend (`frontend/src/`): React Router routes in `App.tsx` (`/` is the Climb, `pages/ClimbPage.tsx`; `/summary`; `/projects/:slug` is a Project; `/status` is readiness; anything else is not-found), all inside `components/Shell.tsx` (header, nav, footer, skip link). `pages/` holds one component per route. `api/` is the typed client: `types.ts` mirrors the API responses, `client.ts` has the fetch wrapper (`ApiError`) and TanStack Query options, `useSummary.ts` combines profile and Projects into loading, error or ready. `useProject.ts` finds one Project by slug in the cached Projects list (so previous and next follow the API's order and cost no request): loading, error, not-found (an unknown slug, distinct from a failed request) or ready. The first Project has no previous link and the last no next; nothing wraps. `components/ProjectGallery.tsx` renders the optional `Project.media` (the API sends none yet) and draws nothing, not even its heading, when there is no picture. `readiness.ts` treats anything other than a 200 or 503 report as "API unreachable". Each route sets its title with `usePageTitle`.
- **The Climb's position (ticket #14). One source of truth**: `src/climb/climb.ts` holds `{ progress, stage, stages, lead, tail }` and nothing else may measure the page for this. `progress` is 0 to 1 (0 = the Trailhead's top edge at the top of the screen, and on the opening screen; 1 = High Camp's top edge at the top of the screen, and below it through the Summit and contact section); `stage` is the current Stage's key (its top edge is above the middle of the screen) or null on the opening screen; `stages` is each Stage's place along the Climb as `{ key, position }`, measured from the real layout, so a long Stage takes more of the Climb; `lead` is 0 to 1 across the opening screen and `tail` 0 to 1 as the Summit section (`#summit`) comes up the screen after High Camp, the two stretches `progress` leaves out, which the scene's camera needs. Stage sections have `id` = the Stage key, which is also the direct-link fragment (`/#ridge`). Only `ClimbPage` starts tracking (`trackClimb(keys, onReach)`, one rAF-coalesced reading per frame from the scroll position, never from what was painted) and stops it on unmount. To read it: outside React, `getClimb()` and `subscribeClimb(listener)` (the scene's camera does this every frame, with no re-render); inside React, `useCurrentStage()` and `useStagePositions()` (change rarely) or `useClimb()` (re-renders on every change of progress; avoid). `scrollToStage(key)` is how to move to a Stage (smooth, or instant under reduced motion; focuses the section). "Stage reached" means a Stage's top edge has risen past three quarters of the way down the screen, decided from scroll position, so a Visitor who flings or jumps past a Stage still reaches it and one who never scrolled reaches none below the fold; each is reported through `recordStageReached(key)` in `visit/visit.ts`, which keeps a per-Visit set so a Stage is sent once however often the page mounts. `AltitudeMeter` (`climb/AltitudeMeter.tsx`) reads only this state (a rail on `lg`, a bottom bar below it) and is meant to be reused by the Expedition. The Climb's light is the `--color-light-*` tokens (one per Stage plus the Summit's), each a surface in `contrast.test.ts`; Stage backgrounds are the `bg-stage-*` gradient tokens. Scroll reveals use the `reveal` utility (CSS scroll-driven, a no-op where unsupported or under reduced motion); never put it on an element taller than the screen.
- **Visits and privacy (ADR 0002, ticket #10). Rules that must not be broken**: the client IP address exists only in memory for one request. It is never stored (Postgres, Redis keys or values), never logged (including error paths and exception messages) and never put in a response. No cookies, no CORS, nothing in local or session storage. The daily salt lives only in Redis, with an expiry; never write it to Postgres or a log. Redis keys must not contain an address either (rate limits use a keyed hash of it). `tests/test_visits.py` greps storage and logs for the address, including a failing request, so keep it passing.
- Visits, backend: `api/v1/visits.py` (routes; `get_client` reads `X-Forwarded-For` straight off the request, not as a declared Header parameter, so it cannot be echoed in a validation error) calls `services/visits.py` (`VisitService`: bots, rate limit, referrer, hash, age limit), which uses `services/clients.py` (`ClientInfo`, whose fields are hidden from `repr`, and `ClientHasher`: HMAC-SHA256 of address and user agent, truncated to 32 hex characters, keyed by the daily salt; the rate-limit key is a different-purpose hash of the address alone), `data/visitor_salt.py` (`DailySaltStore`: `visitor-salt:<UTC date>`, `SET NX EX` to the end of the day plus 5 minutes), `data/rate_limit.py` (fixed-window counters) and `data/visits_repo.py`. `services/referrer.py` keeps the host only (no port, path, query, credentials; IP-literal hosts and the site's own host become nothing), `services/bots.py` is the bot user-agent list (an empty user agent and "HeadlessChrome" count as bots). Redis failure never fails a request: no hash and a warning (class name only), and no rate limiting. Limits and the 24-hour age limit are settings (`VISIT_*`). `BodyLimitMiddleware` caps bodies at 4 KiB. Tables `visits` and `visit_events` (Alembic `0005`); other tables can reference `visits.id`. Stage keys come from `StageKey`; a Project slug must exist in `projects`. Progress has no column: the `visit_progress` and `visits_per_stage` views (ordered by `stages.position`) derive it; `visits_per_stage` is a funnel counting Visits whose Progress is that Stage or higher, so missing events for lower Stages do not break it, and Grafana (ticket #13) reads them. Visit tests use a scratch Redis database (15) and a movable `FakeClock` passed to `create_app(clock=...)`.
- **Contact messages (ticket #11). Rules that must not be broken**: the name, address and text a Visitor types are stored only in `contact_messages` (Alembic `0006`), which has no Visit ID and must not get one. They are never logged, in any path including errors, and never appear in a response other than the Visitor's own field messages. How that is kept true: `NewContactMessage` hides its fields from `repr`; `ContactRepository.create` raises `ContactStorageError` with `from None` because a SQLAlchemy error's text carries the statement's parameters; `MailDelivery` logs the message ID and the error class only; `errors.py` answers contact 422s with our own messages instead of FastAPI's default, which echoes `input`. `tests/test_contact.py` greps the logs and Redis for them over every path, so keep it passing.
- Contact, backend: `api/v1/contact.py` -> `services/contact.py` (`NewMessage` validation, honeypot, rate limit, store) -> `data/contact_repo.py`; `services/mailer.py` (`MailDelivery`, `build_email`) sends through aiosmtplib as a FastAPI background task after the response. The honeypot field is `website`, checked before the rate limit so a bot gets the identical `201` even when over the limit. The limit is the existing `WindowCounter` keyed by `ClientHasher.rate_limit_key` (`contact:<hash>`, one hour, `CONTACT_LIMIT_PER_HOUR`), counted only for valid, non-honeypot messages, and let through when Redis is down. Delivery is one attempt with a timeout and no retry (a retry queue would be a second place holding personal details), only when `SMTP_HOST`, `MAIL_SENDER` and `MAIL_RECIPIENT` are all set. Header injection is refused twice: validation rejects control characters and `build_email` strips them and rejects a multi-address Reply-To. `BodyLimitMiddleware` takes per-path limits (`path_limits`): 32 KiB for contact, 4 KiB elsewhere. `get_client` and `ClientDep` live in `deps.py`. Tests run a real SMTP server in the test process (`tests/mail_helpers.py`, aiosmtpd); its own log is silenced there because it prints every address.
- Contact, frontend: `components/ContactSection.tsx` is the one reusable section (props `links`, `className`; no router or query client needed, so High Camp, ticket #14, can place it). It owns the form states ready, sending, sent, failed and rate limited, and calls `recordEvent({ type: "contact_message_sent" })` after a 201, separately from the message request, which carries no Visit ID. `api/contact.ts` holds the browser-side checks (they mirror the server's, which stays the authority) and `sendMessage`. A permanent `role="status"` region announces sending and the confirmation and takes focus when the form is replaced; failures use `role="alert"`; field errors are tied with `aria-describedby` and focus moves to the first invalid field. The honeypot is `sr-only` inside an `aria-hidden` wrapper with `tabIndex={-1}`. Do not turn on the browser's own validation (the form is `noValidate`) or the messages will differ from the server's.
- Caddy: `X-Forwarded-For` is set with `header_up` (replacing, so a client cannot forge it; the API port is unpublished and uvicorn runs with `proxy_headers=False`). Caddy writes no access log, deliberately, and its error log has request addresses and headers deleted. Do not add a `log` directive to a site block.
- Visits, frontend: `src/visit/visit.ts` starts one Visit (`startVisit()`, called from `main.tsx`, idempotent so strict mode cannot start two) and sends events with `recordEvent()`. The ID is held in module memory only. Events fired before the ID arrives are queued, then sent in order; with no ID (a bot's 204, an error) nothing is sent. All failures are swallowed, requests use `keepalive` (so an event fired as the Visitor leaves still gets out) and `credentials: "omit"`. `device.ts` is the one place the device class is decided. `useProjectOpened` records Project opened once per page view; `CvDownload` records CV downloaded. Stage reached is sent by the Climb through `recordStageReached`; contact message sent is sent by `ContactSection`. `src/visit/anonymity.test.tsx` asserts no cookie or storage use.
- **The 3D scene (ticket #15). One mountain behind the Climb**: `src/scene/` holds it. `SceneHost.tsx` (the only part in the main bundle, mounted by `ClimbPage`) waits until the text has painted (idle callback), checks `support.ts` (the tier, below), then lazy-loads `SceneCanvas.tsx`, which is the scene's own download (about 940 kB, 250 kB gzipped; three.js and React Three Fiber live only there). Nothing mounts where WebGL is unavailable or reduced motion is asked for, and the page is then pixel-identical to ticket #14's. A canvas that fails to start (an error boundary) or loses its context hands the page back the same way. The three tiers (ticket #17) decide whether any of this runs; see the tiers entry below. The layer is `fixed -z-10`, `aria-hidden`, `pointer-events-none`; when the first frame has been drawn the root gets `data-scene="on"`, which the `scene:` Tailwind variant (index.css) reads: Stage backgrounds, the CSS ridgelines and the CSS Summit peak step aside (`scene:bg-none`, `scene:hidden`), and the layer fades in (`scene-layer`, `--duration-scene`). Text stays ordinary page content; each Stage has a scrim on its text side (`bg-scrim-left|right|edge|veil|top`, `scrim-fade`) and the altitude meter a shade (`bg-rail-shade`), all tokens, tuned from sampled pixels so text stays at AA over the scene (worst measured 5.7:1 at 1280 wide and 6.4:1 at 360 wide, in-betweens included). When you change the scene, its poses or a scrim, re-check that by hiding the text (`color: transparent`), screenshotting, and comparing each text rect's worst background pixel against the text colour.
- The scene, how it works: `world.ts` builds everything from one seed (`MOUNTAIN_SEED`): `landform.ts` (five peaks plus crags, pure and seeded through `noise.ts`), `trail.ts` (waypoints to a `CatmullRomCurve3`, with the trail's bench cut into the ground), `terrain.ts` (a jittered triangle grid; `heightAt` is exact on the drawn triangles, so a foot on it stays on the ground; the sun's shade is baked per vertex). `meshes.ts`/`parts.ts` make the geometry (flat-shaded ground with per-face colour, far ranges, pines, trail ribbon, High Camp's tents, stars) in seven or eight draw calls and about 72,000 triangles; `materials.ts` patches Lambert lighting with valley mist, baked shade and first light on the Summit, and holds the sky and star shaders. **Colours come from tokens**: `palette.ts` lists the token names and `readSceneColors()` reads `--color-*` from the stylesheet when the scene starts (the theme block is `@theme static` so every token is written out); sky overhead is the Stage's `light-*`, the horizon its `ember-*`, the Summit's glow `first-light`, and `rock-deep|rock|scree|snow|trail|pine|star` are the scene's own tokens. `light.ts` is the light at a point on the journey (seven keys, mixed linearly); `journey.ts` is the camera.
- The scene's camera and position: one number, the journey `u`, runs 0 (opening screen) to 6 (Summit), the five Stages at 1 to 5. `journeyAt(climb)` makes it from the position store (`progress`, plus `lead` across the opening screen and `tail` across the Summit's stretch; Stages sit where they really are on the page), `settle` eases each leg so the camera comes to rest at every Stage, `poseAt(u, narrow)` gives the pose (`POSE_KEYS`: position, target, field of view, and a picture shift that moves the mountain's interest to the side without text; narrow screens, below 1024 px, get their own framing). `controller.ts` (`SceneController`, plain code) eases the rendered `u` toward the page's (`stepJourney`, which lands exactly on the target, so scrolling back reverses exactly) and applies pose and light each drawn frame. Frames are drawn on demand (`frameloop="demand"`; `invalidate()` on a Climb change and while easing), none while the tab is hidden (`visibility.ts`), pixel ratio is capped at 1.5, and `controller.mount()` returns what disposes every geometry and material when the page is left.
- **The scene's interface for later work (the Hiker, #16; the Expedition game)**: `src/scene/registry.ts`. While the scene is mounted, `getClimbScene()` (or `useClimbScene()` in React, `subscribeClimbScene()` to follow it coming and going) returns a `ClimbScene`: `trail` (`pointAt(t)`, `tangentAt(t)`, `curve`, `length`; t is 0 at the Trailhead and 1 at High Camp), `stages` (each Stage's key, `trailT` and `position` in scene space), `heightAt(x, z)` (the drawn ground), `summit`, `progress()` (the progress value the camera has eased to, 0 to 1), `trailT()` (where on the trail that puts the Hiker) and `subscribe(listener)` (called when the rendered progress changes). A component inside the canvas imports it from `scene/`; nothing needs the scene's internals. Where no scene is drawn, `getClimbScene()` is null.
- Debug view: `/?debug` draws every frame and shows frames per second, milliseconds per frame, triangles, draw calls, geometries, the journey position and the camera; `&at=3.5` pins the camera at that point of the journey; in the console `setScenePose([x, y, z, targetX, targetY, targetZ, fov, shiftX, shiftY])` (or `null`) tries a composition without a reload. Measure performance with it on the target machine; software rendering (headless Chrome) says nothing about a laptop's frame rate.
- **The Hiker (ticket #16)**: the figure on the trail, `src/scene/hiker.ts` (the class `Hiker` plus pure helpers `headingOf`, `turnBetween`, `phaseAt`, `lanternAmount`) and `hikerModel.ts` (`hikerModelUrl`, `loadHikerModel`). It uses only the scene's interface (`trailT()`, `trail.pointAt/tangentAt/length`, `heightAt`, `summit`): position on the trail, feet on `heightAt`, facing the direction of travel (turns around when the Visitor scrolls back; at rest it faces up the trail, and at High Camp toward the Summit). `SceneCanvas` loads it only after the first draw (`onDrawn`): `mediaQuery` (the same cache as the Summary) gives the `hiker` item's `.glb` URL, the GLTFLoader is a dynamic import, and any failure leaves the scene without a Hiker. `SceneController.attachHiker` adds it and calls `hiker.update` in each frame; `settling` stays true while the Hiker moves, turns or fades its walk, so on-demand rendering draws nothing once it is at rest. The walk plays only while moving, from distance: `measureGait` reads the planted foot's travel over the cycle from the animation itself, and `phaseAt(gait, ground)` maps ground walked to the cycle, so a planted foot stays put (measured slip about 7%, against about 53% for an even-rate cycle; `probeHiker()` in the debug view reports it). Cycles are capped at 4 a second, so a fast scroll outruns the legs (the trail is many dozens of Hiker heights long, so no walk can keep pace with a scroll). At rest the Hiker holds the Idle clip's first frame. A lantern (a glow quad and a small box in the left hand) burns while the sky has stars (`lanternAmount(light.stars)`) and fades with the dawn. No scene, no Hiker: nothing is requested where no canvas mounts. Camera keys in `journey.ts` (the Summit view is framed higher and wider than before, since the contact section covers the lower part of the scene and the camp must clear it; on narrow screens the Hiker is only about 20 to 60 px) (positions, wide and narrow shifts) were moved back along the trail so the Hiker is on screen, clear of the text column and the meter, at the opening screen, each Stage and the Summit view; re-check this (and text contrast) if a key or the layout changes. `?debug` adds `window.probeHiker()` (screen position, height, facing, walk, ankles, feet gap, slip, draw calls).
- **The Hiker's model is content**: `content/hiker/hiker.glb` (KayKit Rogue_Hooded, CC0, 229 kB, 3,957 triangles, only `Walking_A` and `Idle`), built by `content/hiker/build-hiker.mjs`; source, licence, changes and hashes are in `content/hiker/CREDITS.md` and the README's Credits. `content/media.yaml` has `hiker: {file: hiker/hiker.glb}`, a path inside `content/` (not `MEDIA_DIR`); the pipeline (`MediaPipeline(store, repo, source_dir, content_dir)`) reads it from there, checks the `glTF` header, stores it byte for byte as `hiker-<hash>.glb` (variant kind `model`, `model/gltf-binary`), and a missing tracked file is an error, not a skip. Do not swap the model without checking its licence (ADR 0001) and updating CREDITS.md.
- **Camera keys, the Hiker and the contrast scan (ticket #16)**: the keys in `journey.ts` were derived, not guessed. `scripts/camera/solve.test.ts` (copy it into `frontend/src/scene/`, set `SOLVE_U`, run with vitest; header explains) searches the smallest camera change and wide picture shift that put the Hiker in a free region of the screen (regions measured from the page) with a clear line of sight to its feet, middle and head; it does not solve narrow screens, whose shifts were set by hand from the scan's Hiker positions (text fills the width there, so at the Long Approach, the Ridge and High Camp the Hiker rests out of frame, which is why narrow `shift.x` may be non-zero, at most 0.35). `scripts/scan.py` (with `scan-text.js`; needs the stack up, `agent-browser`, Pillow) steps the journey in quarter steps, records where the Hiker is and what it overlaps, hides the text and measures each text rectangle's worst background pixels against its colour (WCAG), skipping text under the fixed bottom bar. Re-run it at 1280x800 and 360x740 after any change to a camera key, the layout or the scene's light, and keep every minimum at 4.5 or more (last run: 5.50 at 1280, 5.14 at 360). The Hiker also steps out of the way of the page: `occlusion.ts` (the one place that reads the page) asks `document.elementsFromPoint` over a 3 by 3 grid on its screen box, and the Hiker fades while text, a card, a control or a bar is there, so it never sits half hidden or lowers contrast. On arrival at High Camp it lights its lantern again. `bg-rail-shade` was deepened so the meter's labels hold 4.5 over the brighter High Camp sky.
- **Tiers (ticket #17). One place decides**: `src/tier/`. `decide.ts` is the whole rule as a pure function `decideTier(DeviceReport)`; `device.ts` reads the browser (WebGL 2 context made and released at once, renderer name from `WEBGL_debug_renderer_info` matched against SwiftShader/llvmpipe/software names, plus a `failIfMajorPerformanceCaveat` context for browsers that hide the name; `prefers-reduced-motion`; `navigator.connection.saveData`; `deviceMemory`; `hardwareConcurrency`); `tier.ts` holds the one decision (`chooseTier()` in `main.tsx` before `startVisit(tier)`, `getTier`, `useTier`, `lowerTier`), and writes `data-tier` on the root. **The rule**: reduced motion, no WebGL 2 or software rendering gives still; otherwise an unknown renderer, data saver, nothing known of memory and processors, memory under 4 GB or fewer than 4 processors gives light; otherwise full. A device we know nothing about is light, never full. **`?tier=full|light|still` forces a tier** (it wins over everything, reduced motion included, for tests and for comparing; this machine's software WebGL is always still otherwise). The Visit carries the tier it starts with; a throwing decision serves light and starts the Visit with no tier, so a Visit is never lost; a later downgrade is not recorded. The tier only ever gets lighter (`lowerTier` refuses an upgrade or the same tier), never reloads, never flips back.
- Tiers, light: `scene/quality.ts` (`QUALITY.full|light`). Light is the same landform, trail, light, camera and Hiker with a ground of 96x108 cells instead of 160x180 (about 36,000 triangles against 76,000 with the Hiker), every second pine, half the stars, pixel ratio 1 (full is capped at 1.5) and no antialiasing where the canvas starts light (a context's antialiasing cannot change, so a full tier that drops in place keeps it). Building is pausable work (`scene/steps.ts`: generators that `yield`, run by `drainAsync` in slices of about 8 ms with the main thread handed back between, or synchronously by `drain` in tests), so the world and the geometry no longer block the main thread for 600 ms; the debug view's `window.sceneBuild` reports the build time and longest slice. In-place downgrade: `scene/frameWatch.ts` (`createSlowWatch`, pure) counts frames drawn back to back while the camera eases (the Visitor scrolling): 18 of the last 24 over 45 ms trips it; `SceneCanvas` then builds the light ground in slices and `SceneController.swap` exchanges ground and parts; camera journey, light, Hiker and subscribers are untouched. Context loss or a canvas error calls `lowerTier("still")`. In `?debug` real frames are not watched; `window.simulateFrames(ms, count)` feeds the watch, which is how the browser test drops full to light without a slow machine.
- Tiers, still: `src/still/` (no three.js; `climb/position.ts` holds `journeyAt`, shared with the scene). `StillBackdrop` is a fixed `-z-10` layer where the canvas would have been, rendered by `ClimbPage` only in the still tier, with `data-scene="on"` so the sections step aside as for the scene (scrims and meter shade apply). Seven layers (opening, five Stages, Summit), each the page's own sky gradient token with the picture over it: layer `k` is fully on from journey `u >= k`, the next fades in across the middle of the way (`stillOpacity`), or switches at the halfway point with no fade under reduced motion. A picture is mounted only when the Visitor is within one position of it (the first at once, eager, `fetchpriority=high`; the rest lazy) and is a `<picture>` with AVIF, WebP and JPEG sets, a wide composition from 1024 px up and a narrow one below, and width and height attributes. The tier downloads neither `SceneCanvas` nor the Hiker's model (browser test).
- Stills, content: `content/stills/<position>-<wide|narrow>.png` (tracked, generated, not personal; wide 1600x1000, narrow 390x800 at 1.5x) plus `stills.json`. `frontend/scripts/capture-stills.mjs` drives the real full scene (forced tier, `?debug`), scrolls to each position, waits until the camera and Hiker are at rest, hides everything but the canvas and saves the frame, so the Hiker is wherever the full scene has it (out of frame on narrow screens at some Stages, by design). The media role `stills` (`content/media.yaml`, `app/media/`) renders each at its composition's widths (wide 640/1024/1600, narrow 360/585) in AVIF, WebP and JPEG as `still-<name>-w<width>-<hash>.<ext>`; `/api/v1/media` lists them with `kind: "still"` and `name`. The first capture needs the seed to run, so bootstrapping an empty `content/stills/` means putting any placeholder PNG there first.
- **Pre-rendering (ticket #18). Rules that must not be broken**: the pages are HTML drawn by the real React app on the server side, then hydrated, so a crawler and a link preview see the content. Code that runs during a render must not touch the browser: no `window`, `document`, `localStorage` or `matchMedia` at render time or at module scope, no request, and nothing that starts a Visit. Browser-only work (the tier decision `chooseTier`, `startVisit`, the scene, the still backdrop, the Hiker, `trackClimb`, scroll code, `useHead`'s DOM writes) lives in `main.tsx` or in effects, which do not run on the server. A `useSyncExternalStore` that reads the browser needs a `getServerSnapshot` that is what the server draws (`useTier` says `light`, which draws no backdrop, and the real tier replaces it right after hydration; `VideoCv` and the Climb's hooks do the same). The server's HTML and the browser's first render must match exactly (a mismatch is a console error in production, and the browser test watches for it), so anything that differs between the two belongs in an effect or behind such a snapshot.
- Pre-rendering, how it works: `frontend/src/prerender/` is the server entry (`render.tsx`: `renderPage` puts the content in a `QueryClient`, draws `<App>` in a `StaticRouter` with `renderToString`, and collects the page's head; `fillTemplate` puts the head, the HTML and the embedded data into the built `index.html`), `pages.ts` (the page list, driven by the Projects the API returns; also `/status`, `404.html` and `404-project.html`), `sitemap.ts` (`sitemap.xml`, `robots.txt`) and `run.ts` (the job: fetch `/profile`, `/stages`, `/projects`, `/media` through the same `getJson` the pages use with `setApiOrigin`, draw every page, write the files each in one step, remove files of an earlier run; any failed request or a page drawn in its loading state fails the job). `npm run build` also builds `run.ts` as one file with `vite build --ssr` (`ssr.noExternal`, so the image needs only Node); `infra/caddy/Dockerfile` has a `frontend` stage, a `prerender` target (the job image; runs as root because a new named volume is root's) and the Caddy image, so the pages always name the scripts Caddy has. The job writes to the `site` volume (`/site`), which Caddy mounts at `/srv/pages`. Embedded data: each page carries the queries it was drawn from in `<script type="application/json" id="prerender-data">` (`{siteUrl, state}`, TanStack Query's `dehydrate`, times fixed so the same content gives the same bytes); `main.tsx` calls `hydrate(queryClient, state)` before `hydrateRoot`, so the first render matches and nothing is fetched twice (`staleTime` is infinite). With no embedded data (dev mode) it uses `createRoot`. The JSON escapes `<`, `>` and `&`.
- Pre-rendering, the head: `frontend/src/head/`. `model.ts` builds a `HeadModel` per page kind (`landingHead`, `summaryHead`, `projectHead`, `unlistedHead`) from the content, and `headTags` turns it into meta and link tags (Open Graph, Twitter card, canonical, `noindex`, JSON-LD); `description.ts` builds descriptions (plain text, at most 160 characters, ends at a sentence or a whole word, never on "with" or "and"); `structuredData.ts` is the schema.org Person (name, headline as job title, email, LinkedIn, GitHub, the site's address: nothing else, no phone); `render.ts` writes the tags as HTML (escaped, each marked `data-head`) and `useHead.ts` is the one hook pages use: on the server it hands the model to the collector, in the browser it replaces the `data-head` elements and the title so client-side navigation keeps them current. Titles: landing `<name> | <role>` (the headline up to its first `|`), the Summary `Summary | Ali Saleh`, a Project `<name> | Ali Saleh`. The site's public address is `SITE_URL` (`.env`, default `http://localhost:<CADDY_PORT>`), passed to the job by `compose.yaml`; canonical addresses, the sitemap, `robots.txt` and the absolute preview picture addresses use it, and the landing page's canonical address ends in `/`. Without the job's context (dev mode) the page's own origin is used.
- Pre-rendering, preview pictures: the media pipeline crops a 1200x630 JPEG from each wide still (`images.render_preview`, centred, `still-<position>-preview-w1200-<hash>.jpg`, variant `kind: "still"`, `name: "<position>-preview"`, no AVIF or WebP because every crawler reads JPEG); `/api/v1/media` lists it and the pages read it by name. Landing: `opening`; Summary: `summit`; Projects: `trailhead`, `long-approach`, `steep-switch`, `ridge`, `high-camp` in the API's order, wrapping (a sixth Project shares the first's picture). The settings hash includes the preview size, so changing it re-renders the stills at the next seed. A page whose still is missing simply has no image tags.
- Pre-rendering, Caddy: `infra/caddy/Caddyfile`. A page is `/srv/pages/<path>.html` (`/` is `index.html`); the baked `index.html` is removed from `/srv` (it is only the job's template). `/summary/` redirects (308) to `/summary`. `/robots.txt` and `/sitemap.xml` come from `/srv/pages`; the favicon and `/assets/` from `/srv`. An address with no file is an error 404, and `handle_errors` answers it with `404.html` (any address; the app draws its not-found page), or `404-project.html` for `/projects/<one segment>` (the page drawn for a Project that does not exist, because the router reads that address as one, so it must hydrate that way), keeping the 404 status; a missing asset, favicon, robots or sitemap stays a plain empty 404 and other errors (502) keep their own body. `/status`, the 404 pages are `noindex`. HTML is `Cache-Control: no-cache` (revalidated, `304`), assets stay immutable. `.html` addresses (`/summary.html`, `/index.html`) are 404s, not files. Dev mode: `compose.dev.yaml` puts `prerender` in a profile and drops Caddy's wait for it; Vite serves an empty page that `createRoot` draws, as before.
- Design tokens live in the `@theme static` block of `frontend/src/index.css` (`static` so every token is written out as a CSS variable, for the 3D scene to read): colour (night ground, one sunrise accent, derived from ADR 0001), type scale, spacing, radius, motion durations and easings, focus. The block resets Tailwind's defaults, so only these exist. **Tokens only**: components use token utilities (`text-ink`, `px-gutter`, `animate-rise`), never literals or arbitrary values such as `text-[13px]`, `#fff` or `300ms`. `src/design/tokens.test.ts` fails on any such literal in a component or in the stylesheet outside `@theme`; `src/design/contrast.test.ts` computes WCAG AA contrast for every text colour in use on each surface. Both run in `npm test`, so CI enforces them. Add a new colour to `@theme` before using it, and a new surface to `SURFACES` in the contrast test.
- **No third-party requests from the browser** (ADR 0002): fonts are `@fontsource` packages bundled by Vite; no CDN, analytics, external images or scripts. Anything a page loads must come from our own origin.
- Frontend tests render the real `App` in a memory router with `fetch` stubbed (`src/test/render.tsx`, fixtures in `src/test/fixtures.ts`).
- Pyright runs in `standard` mode, not `strict`, because redis and Starlette's test client are not fully typed.
